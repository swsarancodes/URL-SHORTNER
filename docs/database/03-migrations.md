# Database Migrations

Alembic is used for versioned schema changes.

## Rules

- Every schema change must have a migration.
- Never edit an already-applied shared migration to change history.
- Review autogenerated migrations before running them.
- Separate destructive migrations from ordinary feature work when possible.
- Backward-compatible changes are preferred during rolling deployments.

## Typical workflow

```
change SQLAlchemy models
  -> alembic revision --autogenerate -m "description"
  -> inspect migration
  -> apply locally/test DB
  -> alembic upgrade head
```

## Deployment

Do not rely on every serverless function instance attempting migrations at startup. Run migrations as an explicit deployment/release step or manually for the free-tier project.

## Rollback

Downgrade scripts should be written when practical, but destructive data transformations may not be safely reversible. Backups and careful rollout matter more than pretending every migration can always be rolled back.
